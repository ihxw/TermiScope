# PostgreSQL 与 Docker 验证记录

验证日期：2026-11-05。此记录对应本次 PostgreSQL 部署改造，不表示已有生产实例已经迁移，也不能据此确定此前掉线事故的根因。

## 数据库选择与资源目标

采用 PostgreSQL 17 Alpine，Docker 显式选择 PostgreSQL，连接失败即报错，不回退 SQLite。它提供并发事务和行级锁，能够消除 SQLite 全库单写者的限制；不引入 Redis、PgBouncer 或独立时序服务。

最低 1 核 1 GB 面向小规模监控：应用与数据库各限制 384 MB；Go 使用 `GOMEMLIMIT=256MiB`、`GOMAXPROCS=1`；应用连接池为 12/3，PostgreSQL 最大连接 24、共享缓存 64 MB、单执行节点工作内存 2 MB。资源参数及迁移步骤见 [部署手册](deployment.md#91-docker--postgresql-部署)。

## 并发验证的适用范围

隔离 PostgreSQL 容器运行在 1 CPU、约 998 MB 内存的虚拟机中，数据库容器上限 384 MB。虚拟机采用 **QEMU TCG 软件模拟**，耗时不能当作真实 1C1G 云服务器的性能基准。

数据库并发用例使用最多 12 个连接，同时完成 10,000 条补报、10 台主机合计 250 次心跳更新及 250 次用户查询，校验数据和最终心跳均正确；工作阶段耗时约 40.3 秒。该用例直接调用数据库辅助函数，没有把它描述为 30 秒 HTTP 上报预算内完成的接口压测。

此验证证明兼容性、事务和重试行为，没有测出生产吞吐上限。历史统计仍需处理所选窗口内的原始样本；主机数、探测任务、采样频率、文件传输、历史窗口和磁盘速度都会影响容量。大规模补报应允许幂等重试；达到资源上限时需要提高配置或进一步优化查询，不能承诺任意负载下无瓶颈。

## 复现数据库集成测试

使用专用 PostgreSQL 17 测试实例，设置 `TERMISCOPE_TEST_POSTGRES_DSN` 后执行：

```bash
go test -count=1 -p 1 ./internal/database ./internal/handlers \
  -run 'Test(Postgres|MigrateSQLite)' -v
```

测试会创建独立 schema；原生备份往返测试还需要同主版本的 `pg_dump`、`pg_restore` 和创建测试数据库的权限。不要指向生产实例。缺少连接配置时，真实数据库测试会明确跳过。

此次没有运行生产迁移、发布镜像或正式 Release；验收旧实例时仍应核对原账号登录、主机数量、凭据解密和新心跳。迁移必须保留原 JWT/AES 密钥。

## 最后变更的验证边界

Docker 实测已通过初始化、重启持久化、数据库断连后拒绝鉴权和重新初始化、数据库恢复，以及部署脚本原生备份和停服恢复。测试使用本机构建的服务端和 Web 组装运行镜像，未执行正式多架构镜像发布。

最后的容器迁移试验发现，WAL 模式 SQLite 在只读挂载中可能无法创建共享内存文件。迁移已改为先只读复制停服源库及 WAL/回滚日志到私有临时目录，再读取副本；原文件不变，不使用会忽略 WAL 的 immutable 模式。临时目录需要容纳源库及日志的额外磁盘空间。按用户要求，此项最终修正后未再运行测试，不能将此前迁移函数测试视为最终容器入口已验收。
